# Citation and BibTeX checks of a review

Step 6 of `SKILL.md` runs these scripts on LaTeX source. Each section gives the command, the output format, the known limitations, and how to report the result.

## Clusters and grounding comments: `find_citation_issues.py`

A grounding comment leads with the `% GROUNDING` marker. Both `% GROUNDING: "..."` (and `% GROUNDING: <key> -- "..."`) and the per-key `% GROUNDING <key>: "..."` form are recognized, so a paper that names the key before the colon is not falsely reported as ungrounded. Run `python3 "<skill-dir>/../../scripts/find_citation_issues.py" <root.tex>` over the LaTeX root. The script follows `\input` / `\include` itself and reports each included file by its path, so passing the root is enough. Each stdout line is `<file>:<line>\t<issue>\t<keys>\t<context>` where `<issue>` is `cluster` or `missing-grounding`. The script prints a stderr summary (e.g. `considered 41 cite call(s) across 1 file(s); 1 cluster(s), 41 missing-grounding`). Use it to confirm that the run completed. Known limitations of the scan:

- Biblatex multi-citation commands (`\textcites`, `\autocites`, `\fullcites`) read only the first key group.
- "Nearby grounding" means the comment block attached to the `\cite{}` call: the same line plus the contiguous run of blank and `%`-comment lines directly below it. A comment placed after intervening code or prose is not credited. A quote-less `TODO verify` stub counts as attached (marked, not missing). `/ai-slop:ground` fills such stubs.

- For each cluster, only flag it as a finding if the surrounding prose does not explain what each cited work contributes. A cluster followed by sentences that distinguish each work is fine.
- For missing-grounding, always report the result as a **Grounding to-do** list in the report: every `\cite{}` lacking a grounding comment, by `file:line` and key. Emit this list in every review. (A paper may use the per-key `% GROUNDING <key>: "..."` convention. The script credits it, so do not re-report those citations as ungrounded.) To fill genuinely missing comments, that is, to fetch each cited source and insert a retrieved supporting quote, point the user to `/ai-slop:ground`.

## Missing BibTeX fields: `check_bib_fields.py`

To find the bib files, grep the LaTeX root (and any `\input`-ed files) for `\bibliography{...}` and `\addbibresource{...}` directives and resolve each path. If at least one is found, run `python3 "<skill-dir>/../../scripts/check_bib_fields.py" <bibfile1> <bibfile2> ...` and report each printed entry as a finding. The script uses standard BibTeX required-field semantics (Patashnik's `btxdoc`) and does not honor `crossref` inheritance, so sanity-check flagged entries before reporting them. Skip the check entirely if no bib files are referenced. The script always prints a one-line summary to stderr (e.g. `checked 142 entries across 1 file(s), 0 missing-field issue(s)`). Use it to confirm that the run completed.

## Hallucinated or mismatched references: `verify_references.py`

After the field check, run `python3 "<skill-dir>/../../scripts/verify_references.py" <bibfile1> [<bibfile2> ...] [--mailto you@example.org]` over the same `.bib` files (`--mailto` defaults to `$CROSSREF_MAILTO`). It resolves a DOI at CrossRef, and at doi.org when CrossRef does not hold it (the DataCite DOIs of arXiv and Zenodo), looks each title up in the local DBLP database and, when DBLP has no match, in CrossRef, prefers DBLP's year and venue where DBLP has the paper, accepts any year that the databases record for the work (online-first or print), expands common venue abbreviations before comparing venues, and prints one tab-separated line per entry that is not cleanly verified: `<key>\t<verdict>\t<detail>`, where `<verdict>` is `doi-not-found`, `title-mismatch`, `year-mismatch`, `venue-mismatch`, `not-found`, `unchecked-offline`, or `unchecked`. Report these under **Reference verification**. This check is advisory and needs network access for CrossRef and doi.org. With no network, every lookup returns `unchecked-offline` and the run still exits 0. The script reads DBLP from a local database. The stderr summary names the database, or the script prints that DBLP was not checked together with the `setup_dblp.py` command that downloads the DBLP dump and builds the database. In that case, state under **Reference verification** that DBLP was not checked, and give the user that command in your reply. An entry without a DOI that CrossRef does not hold is then `unchecked`, not `not-found`. Never assert that a reference is fabricated on the basis of a visual check. Treat `doi-not-found` and `not-found` as likely-fabricated only after a sanity check, and for entries that the databases cannot confirm, do a web search to validate before flagging. DBLP's curated BibTeX is the canonical record for CS/SE venues. Prefer the publisher/DOI metadata only when DBLP holds just a preprint of a now-published paper. For an exhaustive non-LLM audit of someone else's submission, point the user to the `hallucite` skill.
